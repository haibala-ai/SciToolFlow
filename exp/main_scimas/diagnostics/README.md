# DeepSeek × SciMas Mini-200 失败分析

本轮低成绩的首要原因是通信失败；此外，已确认 SciMas 执行与 Reviewer 存在会提前终止正确计算的缺陷。剩余问题同时涉及模型规划、工具契约和评分路径覆盖，不能把所有失败解释成模型科学能力不足。

分析对象：`results/deepseek_scimas_mini_20261105_212725_c2/`。共检查 200 份任务记录及对应请求、任务图、工具 observation、终止原因和评分结果；对关键框架问题进行了离线对照与数值复算。本次没有重新请求付费生成/embedding API，没有修改任务、参考答案、评分器、运行代码或原始成绩。

## 1. 原始成绩与统计口径

| 指标 | 数量 | 比例 |
|---|---:|---:|
| 运行完成 | 82 / 200 | 41.0% |
| 工具规划通过 | 70 / 200 | 35.0% |
| 答案通过 | 79 / 200 | 39.5% |
| 运行未完成 | 118 / 200 | 59.0% |

200 份记录均通过原评分流程的证据与资源完整性检查。没有发现本轮成绩由缺失预测文件、篡改证据或评分器搜索未决造成。

82 道完成题中，79 道答案通过、17 道工具规划未通过，其中 16 道答案通过但规划未通过；另外 5 道未完成题的现有工具证据已经满足规划指标。这三个指标独立判断，因此数量不需要相等。

**79/82 只能描述成功提交子集，不能据此推算全体任务的模型准确率。** 当前官方分数保留不变；本报告没有把“可能修复成功”的任务算成成功。

## 2. 118 道未完成题停在什么地方

以下按最终终止原因互斥分类，总数为 118。一个任务可能同时含有多个底层问题，例如成功工具输出被错误解码后，又触发失败次数限制；后文的缺陷数量不能与本表重复相加。

| 最终终止原因 | 题数 | 含义 |
|---|---:|---|
| 生成 API `ConnectTimeout` | 73 | 请求建立连接阶段超时 |
| 生成 API `RemoteProtocolError` | 13 | 响应通信协议中断或异常 |
| 生成 API `ReadTimeout` | 1 | 等待响应超时 |
| embedding `SSLError` | 2 | 检索阶段 TLS/SSL 通信错误 |
| `LocalRepairLimit` | 8 | 局部修复耗尽，包含 Reviewer 误判和真实方法问题 |
| `RepeatedActionFailure` | 6 | 实际均为该工具同参数第一次调用便终止，见下文 |
| Executor 选择不可执行节点 | 4 | 选择不在当轮 ready 集合中的节点 |
| 修复阶段查询未知工具后异常退出 | 3 | 未知名称没有转为可恢复反馈 |
| 角色 JSON 协议重试耗尽 | 2 | 返回内容含 DSML 标记，不能解析为要求的 JSON |
| Reviewer 直接拒绝结果 | 2 | 本次两例均复核出误判 |
| 初始规划次数耗尽 | 1 | 多次仍无法生成满足任务图约束的计划 |
| 数组输出路径验证异常 | 1 | 动态展开访问合法数组元素被框架拒绝 |
| Planner 主动停止 | 1 | 声称候选中缺少可绑定的结构化转换适配器 |
| 单次生成输出上限耗尽 | 1 | 65,536 个输出 token 均用于 reasoning，未生成计划 |

### 2.1 通信故障占未完成题的 75.4%

通信终止合计 **89 题，占全体 44.5%、未完成题 75.4%**。其中 **85 题尚未调用任何科学工具**，通信失败任务的模型请求数中位数为 1，任务耗时中位数约 32.5 秒。

故障有明显时间聚集：北京时间 11 月 6 日 07 点后完成记录中出现 71 次通信终止；末尾 `SMAS-0154` 至 `SMAS-0200` 连续 47 题均通信终止。批处理持续把短暂或持续的连接问题消耗成了新的任务失败。

本轮生成模型是官方直连 `https://api.deepseek.com`、`deepseek-flash`，生成客户端 `trust_env=false`；embedding 使用独立的既有接口与代理配置。因此不能把生成请求失败统一归因于代理。当前记录也不足以判定具体故障跳点、是否是服务端故障，或者把 `ConnectTimeout` 一律判成 TLS 握手超时。未发现将这些错误认定为 HTTP 429 限流的依据。

生成客户端已经对建连错误进行至多两次额外重试；对于可能已经生成并计费的读写中断，设计上不自动重放。因此“完全没有重试”也不符合事实。需要增加的是任务批次熔断、健康恢复与保留失败尝试的续跑机制，而不是无条件重试所有请求。

证据：[逐题统计](task_analysis.json)、[时间分布](timeline.json)、[客户端重试边界](../../../src/models/client.py#L369)。

## 3. 已确认的框架与 Reviewer 问题

### 3.1 关闭失败次数限制的配置被反向解释：6 题

本轮公共配置 `max_failures_per_action=0`。ReAct 将 0 解释为关闭此限制，SciMas 却检查 `count >= 0`，于是第一次结构验证或工具失败就抛出 `RepeatedActionFailure`，排在瞬时重试和局部修复之前。

涉及 `SMAS-0003、0070、0072、0105、0106、0117`。逐条检查确认，终止时对应工具与同参数都只调用了 **1 次**，并非真实重复循环。

离线对照中，对相同脚本式工作流注入一次工具超时：配置为 0 时第一次就失败；配置为 `None` 时执行原有重试并完成。此对照仅证明控制逻辑缺陷，不代表真实六题修复后必然成功。

实际触发错误包括无效输入、工具超时、缺失查询字段，以及下面的原生对象解码错误。修复次数限制以后，这些原始错误仍应得到针对性的修正或反馈。

证据：[离线对照](offline_controls.json)、[六题调用次数](failure_limit_cases.json)、[SciMas 判断位置](../../../baselines/scimas/runtime.py#L629)。

### 3.2 Reviewer 把正确绑定误判成手工复制：4 题

`SMAS-0073、0076、0088、0093` 的任务图包含正确的上游节点绑定。运行时把绑定求值成数值参数后提交工具，Reviewer 却以“实参是 literal，未绑定来源”为由要求重跑，最终耗尽修复次数。

以 `SMAS-0088` 为例：任务图的 `values` 绑定 `parse_study.document.targets`，`stop` 绑定 `split_b.gap_indices[0]`。实际实参自然变成数组和数值 9。Reviewer 将这两项正常求值结果视为绕过来源。已用 dispatch 保存的图哈希逐一匹配当时的任务图，而不是拿后来的修复图替代现场证据。

应把“声明的绑定”“求值后的参数”“实际来源证据”分开展示，并由运行时验证来源关系。不能让语言模型仅从展开后的数值猜测其来源，也不能通过取消来源约束来解决。

### 3.3 待审核状态被误判成过期：2 题

`SMAS-0089、0121` 被判为 stale，但发送给 Reviewer 的现场记录明确为：

- 节点存在于当前任务图；
- `stale=false`；
- 结构验证通过；
- `accepted_for_current_graph=false`，因为本轮正在等待 Reviewer 接受。

同时，框架中的 `valid_nodes` 实际列出的是已接受结果的节点，并非当前图中存在的全部节点。这个命名和状态组合容易让模型误解。应显式区分当前图节点、待审核结果、已接受结果和过期结果。

上述六题原始绑定与状态证据见 [reviewer_evidence.json](reviewer_evidence.json)。

### 3.4 Reviewer 用错误科学判断否定正确工具输出：2 题

| 任务 | Reviewer 的拒绝理由 | 离线核查 |
|---|---|---|
| `SMAS-0111` | 断言特征值不应成双重简并，特征向量不满足方程 | 使用保存的输入矩阵与工具契约规定的**列向量**计算，最大特征方程残差约 `4.44e-16`；独立 NumPy 特征值一致 |
| `SMAS-0022` | 根据当前斜晶胞的长度和角度断言空间群应为 P2/m | 对完整结构及相同容差运行 pymatgen/spglib，仍为工具原报的 Cmmm，国际编号 65；常规晶胞为直角晶胞 |

这两例不能当成工具科学计算出错。数值与结构化科学校验应优先提供可检查证书；Reviewer 提出反对意见时也应有可验证的依据。

证据：[特征值复算](eigen_control.json)、[晶体对称性复算](symmetry_control.json)。

### 3.5 两个确定的类型处理问题

**`SMAS-0009`：合法数组索引被拒绝。** `GetJSONPointer.value` 声明允许 array，但未限定 items。框架把“元素类型未限定”当成“不可访问数组元素”，动态展开后拒绝 `[0]、[1]、[2]`，直接退出。离线对照确认合法 JSON Schema 的 `items=true`、省略 items 均受到同样影响。应保留实际值和接收参数验证，同时支持合法的未限定元素类型。

**`SMAS-0072`：对字典再次做 JSON 解码。** `GetMolecularFrequencies` 返回成功的字典，元数据却写 `decoded_type=json_object`。`accept_result()` 因此执行 `json.loads(dict)`，触发 TypeError，又被 3.1 的缺陷掩盖成 `RepeatedActionFailure`。全工具目录静态扫描发现此类候选 1 项；这不是“所有工具都失败”的证据。

证据：[数组对照](offline_controls.json)、[原生对象接收复现](graph_controls.json)、[目录扫描](catalog_decoding_risk.json)、[解码位置](../../../baselines/scimas/task_graph.py#L267)。

### 3.6 模型犯可恢复错误时，框架过早退出

- **4 题 Executor 错选节点**：`SMAS-0102、0112、0114、0120`。逐条对照实际请求，模型确实选了不在 ready 集合中的节点。框架应拒绝执行并给有限次数的精确纠错反馈，目前是第一次就终止。这同时包含模型错误与错误恢复缺陷。
- **3 题未知名称查询**：`SMAS-0026、0071、0115`。Repair 猜测了不存在的工具名，查询错误向外传播为致命异常；初始 Planner 已有相应错误反馈处理，Repair 路径却没有对齐。应统一 DescribeTools 的逐名称错误反馈。
- **1 题语义前置条件死锁**：`SMAS-0110`。三个根节点要求上游结果具有 `ns`、`unitless` 等单位语义，上游通用数值工具结果却没有相应 metadata，导致无节点可执行。离线求值直接复现 `Unconfirmed or conflicting scientific semantics`。应在图验收时发现不可满足的语义义务，或提供证据支持的单位传递机制；不能编造单位来放行。

## 4. 仍然存在的模型／协议／科学方法问题

框架有问题不代表模型没有错误。以下问题需要分别处理：

| 任务 | 观察 | 判断边界 |
|---|---|---|
| `SMAS-0007` | 初始规划多次出现不合法的模板引用、deliverables 不完整、完整报告错误依赖筛选分支等 | 有真实的任务图规划困难，不能直接放宽科学义务 |
| `SMAS-0017、0025` | Summary 返回 DSML 标签片段，协议重试后仍非合法 JSON | 模型／服务输出协议不符合约定；解析器拒绝有依据，不能无条件吞掉不完整内容 |
| `SMAS-0100` | 非均匀网格上使用简单中心差分，未满足题目明确要求的 `numpy.gradient(..., edge_order=1)` | 属于真实方法偏差，Reviewer 要求修正有依据 |
| `SMAS-0081` | Planner 声称找不到可绑定的结构化转换适配器并停止 | 需要复核候选召回及文本输出适配；不能只凭 Planner 的声明认定整个工具库绝对无法完成 |
| `SMAS-0149` | 一次请求使用全部 65,536 个输出 token 进行 reasoning，响应 `finish_reason=length`，没有计划正文 | 属于生成退化／推理输出耗尽；继续增加上限不是已证实的解决办法 |

此外，3.1 中若干题的无效输入和缺失字段本身仍是模型或工具使用问题。修复框架只是恢复正确诊断和纠错机会，不能保证其自然变成正确答案。

本轮没有发现任务超时 7200 秒、400 次模型请求或 150 万字符上下文限制是主要终止原因。最大已记录输入为 107,789 token；目前没有理由优先通过扩大上下文来解释或修复失败。

## 5. 评分还存在路径覆盖与公开契约问题

### 5.1 不能把 17 道规划未通过都当成科学规划失败

17 道已完成但规划未通过的任务已离线重放评分，结果见 [scoring_diagnosis.json](scoring_diagnosis.json)。其中部分有明确的等价路径覆盖问题：

- **`SMAS-0098`**：评分节点要求把三个初始分布一次批量矩阵乘法；实际分别对每行执行矩阵乘法，提交答案正确。批量与逐行分支应在有完整来源和观察证据时等价。
- **`SMAS-0080`**：评分要求批量 `cdf(z)`，实际逐项执行 `sf(-z)`；对标准正态分布结果相同，但精确参数模式不匹配。
- **`SMAS-0067`**：评分要求乘法前给一侧矩阵除以 3，实际先计算散布矩阵，再除以 3。评分需要核验后续真实除法证据，而不应只认一个运算顺序。
- **`SMAS-0013`**：工具调用使用原始 SMILES，评分绑定要求使用 canonical SMILES 的原样字符串；虽然结构查询参数及结果正确，字符串绑定仍不匹配。应核查完整图身份与来源约束后判断，不能只凭相同分子量接受所谓等价结构。

**尚未把全部 17 题认证为等价路径。** 部分题可能确实缺少必要执行证据；科学答案相同也不能代替编排证据。评分修复需要增加有边界的、可核验的路径证书与反例，而不是凭最终答案正确便补发规划分。

### 5.2 三道答案失败均需要先对齐公开契约

| 任务 | 实际与评分差异 | 公开说明的问题 | 应如何处理 |
|---|---|---|---|
| `SMAS-0059` | `recovered_inchi_*` 填写了 InChI 字符串，评分预期恢复出的 SMILES | 字段名容易误解；公开 schema 只声明 string，缺少表示形式说明 | 明确该字段是 InChI 回转得到的 SMILES；用不含答案的字段描述说明 |
| `SMAS-0060` | 用公式组成工具的平均原子量得到质量，例如 `62.06784`，评分采用 RDKit 的 `62.068` | 公共题目要求 average mass，却没有明确两套工具采用的原子量口径 | 为该读数指定一致的质量定义／工具依据；不能泛化放宽到错误质量也能过 |
| `SMAS-0078` | 返回上三角压缩距离向量，评分要求完整方阵 | 题目与 array schema 未明确矩阵形状；已输出向量对应的距离数值与完整方阵上三角一致 | 明确矩阵维度、对角线与行列物种顺序；若允许压缩表示，应执行严格重建验证 |

对应的公开字段约束、提交值与参考值见 [answer_contract_cases.json](answer_contract_cases.json)。

这些题按当前判据仍然失败。问题是公开要求、答案契约和评分口径没有充分对齐，不应将三例简单描述成三次科学推理错误，也不应不经审核直接改分。

## 6. 效率问题如何放大故障

| 已记录资源 | 数量 |
|---|---:|
| 生成请求 | 5,308 |
| 科学工具调用 | 2,380 |
| DescribeTools 调用 | 218 |
| 已知输入 token | 108,820,916 |
| 已知输出 token | 13,085,665 |
| 缺少 token usage 的失败请求 | 87 |

Reviewer 2,658 次请求、Executor 1,676 次请求，两者合计占约 **84.0% 的已知输入 token**。提供方报告的输入缓存命中合计约 6,628 万 token，占已知输入约 60.9%；这说明有缓存利用，不能说缓存完全没生效。但重复发送完整图和累计证据仍有显著成本，且错误修复会造成重复执行，例如 `SMAS-0073` 最终有 112 次科学工具调用。

完成任务的模型请求数中位数为 42.5，任务耗时中位数约 529 秒。多次模型往返提高了遭遇通信故障的机会，但不能用这一点替代本轮明显的连接故障聚集事实。

上述数字是已观察 usage，不是完整账单；87 次失败请求的未知 token 不能按 0 计费或据此推算费用。分角色统计见 [request_overhead.json](request_overhead.json)。

## 7. 建议处理顺序

1. **先恢复实验可靠性**：为连续通信失败增加批次熔断与健康检查，保留尝试历史，区分基础设施失败和能力失败；对可能已计费请求的重放制定明确策略。后续重跑仍报告完整固定题集，不能删除失败题来抬高成绩。
2. **修复执行层确定缺陷**：统一失败次数限制的关闭语义，修正原生对象解码和数组 schema 路径处理，给 Executor 与 Repair 的可恢复错误提供一致反馈。
3. **修复 Reviewer 的证据表达与验证**：显式展示原始绑定及求值参数，分开待审核和过期状态，使用确定性数值证书支持科学审查；保留对真实错误方法的拒绝。
4. **对齐评分与公开任务契约**：先补矩阵形状、表示形式和质量口径，再为有实际执行证据的等价路径补可验证规则及反例；不能把模型跑通作为任务质量标准。
5. **最后做效率优化和对照复测**：削减角色无关上下文、避免无效重跑，保持可检索原始观察。先用上述失败类型代表题验证，再做完整 200 题对照，记录模型、工具、评分和运行配置版本。
